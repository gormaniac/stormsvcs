## 1. Per data item: which EVE event and field supplies it (8.0, with 7.0 differences) and the config it needs

### Takeaway
EVE covers most of the current tshark extraction list. That includes TLS leaf and chain DER (base64), SNI, JA3/JA3S/JA4, the SSH banner, the RDP client name and keyboard layout, HTTP/1 and HTTP/2 UA, Host, URI and server headers, file bodies through fileinfo and file-store v2 (sha256-named), FTP-DATA, SMTP envelope, headers and attachments. Two items are not available. The SSH server host key is not logged. The SIP User-Agent and Server headers are not logged either, although 8.0 can match `sip.user_agent` in rules. A raw .eml is only available through `smtp.raw-extraction`, which cannot run alongside MIME decoding.

### Cited Findings
**TLS (event_type `tls`)**
- Default (non-extended) fields are `subject` and `issuerdn`, plus `session_resumed`. Extended logging adds `serial`, `fingerprint` (SHA1), `sni`, `version`, `notbefore`/`notafter`, `ja3`, `ja3s`, `ja4`, `client_alpns` and `server_alpns`. Custom logging allows `certificate` ("The TLS certificate base64 encoded"), `chain` ("The entire TLS certificate chain base64 encoded") and `client_handshake`/`server_handshake` (cipher, extension and sig-alg u16 lists in wire order). — [EVE format doc, TLS](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)
- The 8.0 config comment lists the full custom set: `[subject, issuer, session_resumed, serial, fingerprint, sni, version, not_before, not_after, certificate, chain, ja3, ja3s, ja4, subjectaltname, client, client_certificate, client_chain, client_alpns, server_alpns, client_handshake, server_handshake]`. It also warns: "WARNING: enabling custom disables extended logging." Whatever you need must therefore be listed explicitly. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- In code, `certificate` is the first cert in the server's `certs` list (the leaf), as `SCJbSetBase64(js,"certificate", cert->cert_data…)` on `TAILQ_FIRST`. `chain` is a JSON array holding every cert in that list, leaf included, each base64 DER. Python can do `base64.b64decode()` to get DER directly. — [src/output-json-tls.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json-tls.c)
- 8.0 schema TLS fields include `subjectaltname`, `client.*` (client cert subject, issuer, serial, fingerprint, certificate, chain, SAN), `client_handshake.*`, `server_handshake.*`, `ja3.hash`/`ja3.string`, `ja3s.hash`/`ja3s.string` and `ja4`. The 7.0 schema has `certificate`, `chain`, `ja3`, `ja3s`, `ja4` and `client.*`, but no `subjectaltname`, ALPN or handshake fields. — [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json), [schema 7.0](https://github.com/OISF/suricata/blob/main-7.0.x/etc/schema.json)
- JA3/JA4 enablement (8.0): `app-layer.protocols.tls.ja3-fingerprints` and `ja4-fingerprints`. The comment says "If not specified it will be disabled by default, but enabled if rules require it." Set both to `yes`. The doc says: "JA3 and JA4 must be enabled in the Suricata config file." — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in), [EVE format doc](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)
- 7.0 difference: on top of `ja4-fingerprints`, the EVE `tls` logger has its own `ja4: off` switch, documented as "ja4 hashes in tls records will never be logged unless the following is set to on. (Default off)". The same switch exists for `quic`. — [suricata.yaml.in 7.0](https://github.com/OISF/suricata/blob/main-7.0.x/suricata.yaml.in)
- Build flags: `--disable-ja3` and `--disable-ja4` exist in configure, and both default to enabled. `--disable-hashing` also disables ja3 and filestore. — [configure.ac](https://github.com/OISF/suricata/blob/main-8.0.x/configure.ac), [command-line options](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/partials/options.rst)
- Suricata emits JA4 (client) only. The schema has no `ja4s` field. JA4 is also logged for QUIC (`quic.ja4`). — [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json), [EVE format doc QUIC](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)
- A separate `tls-store` output can write certificate chains to disk (`certs-log-dir`). — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- `tls-log` (the non-EVE text output) is deprecated in 8.0 and will be removed in 9.0. — [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst)

**SSH (event_type `ssh`)**
- The only fields are `ssh.client|server.proto_version`, `software_version`, `hassh.hash` and `hassh.string`. HASSH needs `app-layer.protocols.ssh.hassh: yes`. — [EVE format doc SSH](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst), [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json)
- **Confirmed: there is no SSH host key.** The Rust SSH logger emits only `client`, `server`, `proto_version`, `software_version`, `hassh`, `hash` and `string` ([rust/src/ssh/logger.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/ssh/logger.rs)). The parser recognises the `KexdhReply` (31) message code and parses `server_host_key_algs` from KEXINIT, but nothing extracts the key blob ([rust/src/ssh/parser.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/ssh/parser.rs)).
- The 8.0 upgrade notes say the rule keywords `ssh.protoversion` and `ssh.softwareversion` were removed (rule language only, not logging). — [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst)

**RDP (event_type `rdp`)**
- `rdp.event_type` takes one of `initial_request`, `initial_response`, `connect_request`, `connect_response` or `tls_handshake`. The `connect_request` event carries `rdp.client.client_name`, `rdp.client.keyboard_layout` (locale name such as "en-US"), `build`, `version`, `desktop_width`/`height`, `color_depth`, `keyboard_type`, `product_id`, `capabilities` and others, plus `channels` and the `cookie` from `initial_request`. `tls_handshake` gives `x509_serials` only, not the certificates. — [EVE format doc RDP](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst), [schema](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json)
- The parser is commented out by default in suricata.yaml.in (`rdp: #enabled: yes`), while the EVE `- rdp` logger is listed. Enable it explicitly. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)

**HTTP/1 and HTTP/2 (event_type `http`, with an `http.http2` sub-object for h2)**
- Base fields are `hostname`, `url`, `http_user_agent`, `http_content_type` and `cookie`. Extended adds `length`, `status`, `protocol`, `http_method` and `http_refer`. `custom: [...]` accepts about 50 named headers, including `server`, `content-type`, `location` and `set-cookie`. `dump-all-headers: both|request|response` emits `request_headers`/`response_headers` arrays of `{name,value}`. — [EVE format doc HTTP](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst), [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- If `dump-all-headers` is set, `custom` is redundant. The code warns "No need for custom as dump-all-headers is already present". — [src/output-json-http.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json-http.c)
- The HTTP/2 logger always writes `request_headers`/`response_headers` arrays and maps the `user-agent` header to `http_user_agent`. The `http.http2` sub-object holds `stream_id`, `request`/`response` `settings`, `error_code`, `priority` and so on. — [rust/src/http2/logger.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/http2/logger.rs), [schema](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json)
- HTTP request and response bodies are not in the `http` event. They come out as files (see the fileinfo/file-store item below). Base64 bodies (`http_request_body`, `http_response_body`) exist only in alert metadata (`alert.http-body: yes`), bounded by libhtp body limits. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in), [schema](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json)
- 8.0 replaces libhtp with a Rust port that is built into suricata. HTTP/1 URIs containing spaces are now parsed differently (`GET /a b HTTP/1.1` gives URI `/a b`). — [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst)

**Files (event_type `fileinfo`, output `file-store` v2)**
- `fileinfo` fields are `filename`, `size`, `state`, `gaps`, `stored`, `storing`, `file_id`, `md5`/`sha1`/`sha256` ("when … there are no gaps"), `magic` (libmagic), `start`/`end` offsets, `tx_id` and `sid`. The common header and the parent protocol's object (for example `http`, `smtp`, `email` or `ftp_data`) come with it. — [EVE format doc fileinfo](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)
- File extraction protocols are HTTP, SMTP, FTP, NFS, SMB and HTTP2. file-store v2 names each file by SHA256 under `filestore/<first two hex chars>/`, which de-duplicates automatically. The optional `write-fileinfo` writes `<SHA256>.<SECONDS>.<ID>.json`. `file-store.stream-depth: 0` means unlimited, and it can't be set lower than `stream.reassembly.depth`. — [file-extraction.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/file-extraction/file-extraction.rst)
- Without a `filestore` rule, nothing is stored unless `file-store.force-filestore: yes` is set. file-store forces SHA256 "as it uses the SHA256 as the file naming scheme". `eve.files.force-hash: [sha256,…]` forces hashes in fileinfo. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in), [file-extraction.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/file-extraction/file-extraction.rst)
- Body size limits that truncate files are `libhtp.default-config.request-body-limit`/`response-body-limit` (the shipped default is 100 KiB) and `stream.reassembly.depth` (1 MiB default). — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in), [file-extraction.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/file-extraction/file-extraction.rst)

**FTP / FTP-DATA**
- `ftp` events carry `command`, `command_data`, `reply[]`, `completion_code[]`, `dynamic_port`, `mode` (passive or active) and `reply_received`. `ftp_data` events carry `filename` and `command` (for example RETR or STOR). The file contents come through fileinfo and file-store, since FTP is a supported extraction protocol. — [EVE format doc FTP/FTP_DATA](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst), [file-extraction.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/file-extraction/file-extraction.rst)
- `autofp-scheduler: ftp-hash` keeps an FTP flow and its ftp-data flows on the same thread. The docs say this avoids a "concurrency issue in recognizing ftp-data flows due to processing them before the ftp flow got processed". — [runmodes.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/performance/runmodes.rst), [suricata.yaml.in](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)

**SMTP (event_type `smtp`, with `smtp` and `email` objects)**
- `smtp.{helo, mail_from, rcpt_to}` holds the envelope. `email.{from, to, cc, date, subject, message_id, x_mailer, received, url, attachment[], body_md5, subject_md5, has_exe_url, has_ipv4_url, has_ipv6_url, status}` holds the message (same in the 7.0 and 8.0 schemas). — [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json)
- The EVE `smtp` options are `extended: yes` (bcc, message-id, subject, x_mailer, user-agent) and `custom: [reply-to, bcc, message-id, subject, x-mailer, user-agent, received, x-originating-ip, in-reply-to, references, importance, priority, sensitivity, organization, content-md5, date, relays]`. `md5: [body, subject]` is also available (body MD5 needs `app-layer.protocols.smtp.mime.body-md5: yes`). The MIME decoder settings are `decode-mime`, `decode-base64`, `decode-quoted-printable`, `header-value-depth: 2000` and `extract-urls`. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- Attachments are extracted as files (fileinfo and file-store). **Raw message**: `app-layer.protocols.smtp.raw-extraction: true` stores the whole conversation as a file named "rawmsg", including SMTP headers and body. It "is incompatible with `decode-mime`. If both are enabled, `raw-extraction` will be automatically disabled." — [suricata-yaml.rst, SMTP](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/configuration/suricata-yaml.rst)
- The SMTP parser is C (`src/app-layer-smtp.c`, about 4.5k lines) and the MIME decoder is Rust (`rust/src/mime/smtp.rs`). — [app-layer-smtp.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/app-layer-smtp.c), [rust/src/mime/smtp.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/mime/smtp.rs)
- The EVE format doc has no SMTP or SIP sections, so the schema is the only authoritative field list. — [EVE format doc](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)

**SIP (event_type `sip`)**
- The 8.0 schema SIP fields are `method`, `uri`, `version`, `code`, `reason`, `request_line`, `response_line` and the parsed `sdp.*` (origin, session_name, connection_data, media_descriptions, and so on). The 7.0 schema has only the first seven, without SDP. — [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json), [schema 7.0](https://github.com/OISF/suricata/blob/main-7.0.x/etc/schema.json)
- **Confirmed: there is no User-Agent or Server header in SIP EVE output.** The Rust SIP logger only writes `code`, `method`, `reason`, `request_line`, `response_line`, `uri` and `version` ([rust/src/sip/log.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/sip/log.rs)). 8.0 does have detection sticky buffers `sip.user_agent`, `sip.from`, `sip.to`, `sip.via`, `sip.content_type` and `sip.content_length` ([rust/src/sip/detect.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/sip/detect.rs), [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst)).
- 8.0 SIP also runs over TCP and is detected by pattern matching. The parser is commented out by default (`sip: #enabled: yes`). — [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst), [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)

**Parser implementation language (verifying the earlier claim)**
- 8.0 still uses C for TLS (`src/app-layer-ssl.c`, about 3.4k lines), SMTP (`src/app-layer-smtp.c`) and **FTP** (`src/app-layer-ftp.c` contains `FTPParseRequest` and `FTPParseResponse`, with Rust helpers in `rust/src/ftp/`). Stream reassembly is also C (`src/stream-tcp-reassemble.c`). SSH, RDP, SIP and HTTP2 are Rust, and HTTP/1 is the new Rust libhtp. **So the earlier claim that FTP is Rust is only partly right: the FTP parser loop is C.** — [app-layer-ftp.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/app-layer-ftp.c), [rust/src/ftp/mod.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/ftp/mod.rs), [app-layer-ssl.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/app-layer-ssl.c), [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst)

### Inferences
- A minimal 8.0 EVE config for this service would be:
  - `tls: {custom: [subject, issuer, serial, fingerprint, sni, version, not_before, not_after, certificate, chain, ja3, ja3s, ja4, subjectaltname, client_alpns, server_alpns, session_resumed]}` together with `ja3-fingerprints: yes` and `ja4-fingerprints: yes`.
  - `http: {extended: yes, dump-all-headers: both}`.
  - `ssh` with `hassh: yes`, plus `rdp`, `sip`, `ftp`, `http2` and `files: {force-hash: [md5, sha1, sha256]}`.
  - `smtp: {extended: yes, custom: [...]}`.
  - `file-store: {version: 2, enabled: yes, force-filestore: yes, stream-depth: 0}`.
  - Raised `libhtp` body limits and `stream.reassembly.depth`.
- `custom` disables `extended`, so a TLS config using `custom` must list every field explicitly.
- Workaround for SIP UA (untested): a rule such as `alert sip any any -> any any (sip.user_agent; pcre:"/(?P<flow_sip_ua>.+)/"; …)` could capture the header into a flowvar. The metadata output would then log it in `metadata.flowvars`. This is not verified to work and would need testing.
- 8.0 removes the default logging of app-layer metadata with alerts (see the upgrade notes). Read protocol data from the protocol events, not from alerts.

### Gaps
- I could not confirm whether `chain` includes the leaf in every case (for example a resumed session, or TLS 1.3 where the Certificate message is encrypted). Without keys, Suricata sees no TLS 1.3 server certificate. Wireshark/tshark sees one only when a key log is supplied. This is inferred from the protocol, not verified from a Suricata test.
- I did not verify the exact list of HTTP/1 `custom` header names accepted in 8.0, beyond the doc example list.
- I did not test whether file-store emits FTP-DATA files in both active and passive modes.

## 2. Flow records: EVE `flow` and `netflow`

### Takeaway
`flow` is a bidirectional record per Suricata flow. It carries the 5-tuple oriented client to server, `app_proto` (plus `_ts`, `_tc` and `_orig`), packet and byte counts per direction, start/end/age, state, reason (`timeout`/`forced`/`shutdown`/`tcp_reuse`), TCP flag hex per direction, `vlan` and `ip_v`. It has no `pcap_cnt`. `netflow` produces two unidirectional records. Direction normally follows the first packet, but Suricata can swap it after protocol detection on midstream TCP and on UDP. This can disagree with a "client = SYN sender" rule only in midstream or UDP cases.

### Cited Findings
- Flow fields are `pkts_toserver`/`toclient`, `bytes_toserver`/`toclient`, `bypassed.*`, `start`, `end` (last packet), `age`, `bypass`, `state` (new, established, closed, bypassed), `reason`, `alerted`, `action`, `tx_cnt` and `exception_policy[]`. — [EVE format doc Flow](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)
- The 8.0 schema adds `elephant`, `elephant_direction`, `emergency`, `wrong_thread` and `tx_cnt` to `flow`. The 7.0 schema lacks the elephant fields, `wrong_thread` and `tx_cnt`. `netflow` has `pkts`, `bytes`, `start`, `end`, `age`, `min_ttl`, `max_ttl` and `tx_cnt` (`tx_cnt` is 8.0 only). — [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json), [schema 7.0](https://github.com/OISF/suricata/blob/main-7.0.x/etc/schema.json)
- The flow logger sets `app_proto`, `app_proto_ts`, `app_proto_tc`, `app_proto_orig` and `app_proto_expected`. It also sets the `reason` values `tcp_reuse`, `forced`, `shutdown`, `timeout` and `unknown`, `wrong_thread`, `elephant`, and `tcp.tcp_flags`, `tcp_flags_ts` and `tcp_flags_tc` (hex strings) plus `tcp.state`. It writes `vlan` (up to 3 IDs) and `ip_v`. `community_id` is added through `EveAddCommonOptions(..., f, ..., LOG_DIR_FLOW)`. — [src/output-json-flow.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json-flow.c)
- The schema `tcp` object includes booleans `syn`, `fin`, `rst`, `psh`, `ack`, `urg`, `ecn` and `cwr`, plus `ts_gap`/`tc_gap`, `ts_max_regions` and urgent OOB fields. — [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json)
- Flow event orientation: the src and dst fields come from the flow's src/dst unless `FLOW_DIR_REVERSED` is set, in which case they are swapped. `timestamp` is `TimeGet()` at log time, not the flow start. — [src/output-json-flow.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json-flow.c)
- `FlowSwap()` (which sets `FLOW_DIR_REVERSED`) is called only from app-layer protocol detection. For TCP this happens only when the session was picked up midstream (`STREAMTCP_FLAG_MIDSTREAM` without `MIDSTREAM_SYNACK`) and the probing parser says "reverse". For UDP it happens whenever protocol detection returns `reverse_flow`. — [src/app-layer.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/app-layer.c), [src/flow.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/flow.c)
- Flow timeouts default to TCP new 60 s, established 600 s and closed 60 s, and UDP/ICMP/default new 30 s and established 300 s, with emergency variants. The flow memcap is 128 MiB and `emergency-recovery` is 30 %. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- The suricata.yaml reference defines the states. TCP new is the handshake, established follows the handshake, and closed follows RST or FIN. For UDP, new means packets from one direction only and established means packets from both directions. — [suricata-yaml.rst Flow Time-Outs](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/configuration/suricata-yaml.rst)
- At shutdown the flow manager marks remaining flows with `FLOW_END_FLAG_SHUTDOWN`, so they are logged with `reason: "shutdown"`. — [src/flow-manager.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/flow-manager.c), [src/output-json-flow.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json-flow.c)
- A forum maintainer explains that a flow is logged when it is evicted from the hash after its timeout. — [forum: app_proto failed](https://forum.suricata.io/t/several-app-proto-in-flows-appears-as-failed/640)
- Tunnels: the schema has a top-level `tunnel{src_ip, dest_ip, src_port, dest_port, proto, depth, pcap_cnt, pkt_src}` and `parent_id`. `CreateEveFlowId` emits `parent_id` when `f->parent_id` is set. `ether{src_mac, dest_mac, ether_type, src_macs, dest_macs}` is gated by the EVE `ethernet: yes` option. — [schema 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/etc/schema.json), [src/output-json.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json.c), [suricata.yaml.in](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- ICMP: the common header carries `icmp_type`/`icmp_code` for ICMPv4 and ICMPv6, and `ip_v` 4 or 6. ICMP flows pair a type with its counterpart (for example echo 8 with reply 0) through `ICMPv4GetCounterpart`. ICMPv4 error messages do not update flow "seen" state, because they belong to the embedded flow. — [src/output-json.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json.c), [src/flow-util.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/flow-util.c), [src/flow.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/flow.c)
- `stream.midstream` defaults to false ("don't allow midstream session pickups"), and `async-oneside` defaults to false. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in), [suricata-yaml.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/configuration/suricata-yaml.rst)

### Inferences
- Differences from a dpkt flow table:
  - Suricata's key includes VLAN IDs (the flow logger writes `f->vlan_id`), and the flow hash may include other fields such as livedev or tenant. A dpkt key of 5-tuple plus start time will merge flows that Suricata keeps separate by VLAN.
  - Suricata splits flows on timeout (a TCP flow idle for more than 600 s, or a UDP flow idle for more than 300 s, starts a new flow) and on TCP port reuse (`tcp_reuse`).
  - Raise the timeouts if dpkt flows must map 1:1.
- Offline, time advances by packet timestamps, so all remaining flows are flushed at the end of the pcap with `reason: shutdown`. Flows idle longer than the timeout inside the pcap are logged earlier with `reason: timeout`.
- With `midstream: false`, TCP flows without a SYN still get `flow` records, but no app-layer parsing happens. Set `stream.midstream: true` to match tshark, which dissects midstream. This also turns on the direction-swap logic.
- "Client = SYN sender" agrees with Suricata's `toserver` for any flow that starts with a SYN. For UDP, Suricata may reverse direction (for example when the first packet seen is a DNS response). dpkt's "first packet sender" would then disagree. Normalise by comparing endpoints, not by trusting `src_ip`.

### Gaps
- `netflow` direction semantics (which record is first, and whether the two halves share a `flow_id`) are not documented beyond the field list. Test empirically.
- I did not check whether GRE, VXLAN, Geneve or Teredo inner flows emit `tunnel` on every event type or only on alerts. `tunnel` is documented in the schema but has no prose description.

## 3. Correlating EVE to packets and dpkt flows (pcap_cnt, timestamps, flow_id, community_id, pitfalls)

### Takeaway
`pcap_cnt` is a 1-based global counter incremented for every packet libpcap hands to Suricata. For a single pcap read without a BPF filter it equals tshark's `frame.number`. It appears on packet-triggered events (alert, anomaly, app-layer, fileinfo) as the packet that caused the log. It is missing from `flow`/`netflow` records and from events emitted on flow-timeout or shutdown pseudo-packets. `flow_id` is only valid within one run. `community_id` (SHA1 of the 5-tuple, direction-independent) can be computed in Python with `communityid` to join to dpkt flows. Pair it with start and end times, and be careful with ICMP.

### Cited Findings
- The docs say "`pcap_cnt` contains the packet number in the pcap. This can be used to look up a packet in Wireshark", and "the pcap fields are only available on 'real' packets, and are omitted from internal 'pseudo' packets such as flow timeout packets". `pcap_filename` requires `eve-log.pcap-file: true`. — [EVE format doc, PCAP fields](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst), [suricata.yaml.in](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- Code: `p->pcap_cnt = ++pcap_g.cnt;` runs in `PcapFileCallbackLoop` for each packet from `pcap_dispatch`, before decoding. A packet that fails to copy is still counted. — [src/source-pcap-file-helper.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/source-pcap-file-helper.c)
- `pcap_g` is zeroed in `PcapFileGlobalInit` (memset). — [src/source-pcap-file.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/source-pcap-file.c)
- The EVE header writes `pcap_cnt` only `if (p->pcap_cnt != 0)`. — [src/output-json.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json.c)
- The flow event builder has no `pcap_cnt` at all (only timestamp, flow_id, vlan, tuple and ip_v). — [src/output-json-flow.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json-flow.c)
- `pkt_src` shows the origin, for example `"wire/pcap"` or `"stream (flow timeout)"` for pseudo-packets. — [EVE format doc examples](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)
- Redmine #8224 (7.0.8): an HTTP app-layer alert logged with `pkt_src: "stream (flow timeout)"` was attributed to the wrong packet because of timestamp handling on the pseudo-packet. Fixes were backported to 7.0.x and 8.0.x. — [Redmine #8224](https://redmine.openinfosecfoundation.org/issues/8224)
- Timestamps are ISO-8601 with microseconds and a UTC offset (for example `2023-09-18T06:13:41.532140+0000`) via `CreateIsoTimeString(p->ts)`. App-layer events use the triggering packet's time, and flow events use `TimeGet()`. — [src/output-json.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json.c), [src/output-json-flow.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json-flow.c), [EVE format doc](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)
- `flow_id` "correlates the network protocol, flow logs EVE data and any evidence … alert … fileinfo … anomaly logs". It is emitted from `FlowGetId(f)`. — [EVE format doc flow_id](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst), [src/output-json.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json.c)
- Community ID is enabled with `community-id: true` and `community-id-seed: 0` (range 0–65535) under eve-log. The config comment says it gives "a predictable flow ID that can be used to match records to output of other tools such as Zeek". — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- Suricata's implementation is SHA1 over `seed, src, dst, proto, pad0, sp, dp`, with endpoints ordered smaller first, base64-encoded with a "1:" prefix. For ICMP and ICMPv6, `sp` = `icmp_s.type` and `dp` = `icmp_d.type`, where `icmp_d.type` is the counterpart type, or left at 0 when none exists. — [src/output-json.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json.c), [src/flow-util.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/flow-util.c)
- The spec uses the same SHA1 ordering. For ICMP it uses `map_icmp_to_ports(type, code)`, "inspired by Zeek". The spec also notes that implementations may differ, for example on whether VLAN IDs are included. — [community-id-spec](https://github.com/corelight/community-id-spec)
- Python: `pip install communityid`. Usage is `communityid.CommunityID(seed).calc(FlowTuple.make_tcp(...))`. The package ships `community-id-pcap`, which reads pcaps through dpkt. — [pycommunityid](https://github.com/corelight/pycommunityid)
- Checksums: `pcap-file.checksum-checks: auto` (the default) samples packets and turns validation off if invalid checksums look like offload. `-k none` disables checks, and `-k all` forces them. `stream.checksum-validation: yes` makes the stream engine reject bad-checksum packets. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in), [options.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/partials/options.rst), [src/source-pcap-file-helper.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/source-pcap-file-helper.c)
- In 8.0, `stream.checksum-validation` no longer affects the checksum rule keywords. — [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst)
- Limits that silently drop data are `stream.reassembly.depth: 1 MiB`, `stream.memcap: 64 MiB`, `stream.reassembly.memcap: 256 MiB`, `flow.memcap: 128 MiB`, `defrag.memcap: 32 MiB` and per-protocol `max-tx` values. All memcap-policy settings default to ignore. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)

### Inferences
- `pcap_cnt` equals the tshark frame number when Suricata reads exactly one file with no `-F` BPF filter, because libpcap drops filtered packets before the callback. With `-r <dir>` the counter is global and is not reset by the helper. Per-file numbering then breaks, so run one file per invocation.
- An app-layer event's `pcap_cnt` is the packet that completed or triggered logging the transaction. That is usually the last packet of the request or response, for example the packet carrying the TLS Certificate or the HTTP response end. It is not the first frame of the transaction, as a tshark per-frame extraction would give. Transactions logged at flow end (when a response never completed) have no `pcap_cnt`, so fall back to `flow_id` and the timestamp.
- Join strategy:
  1. Compute the Community ID in Python for each dpkt flow, using seed 0 and the same tuple.
  2. Map Suricata `flow` records by `community_id` plus a time overlap of `[start, end]`. This handles 5-tuple reuse, since Community ID has no time component.
  3. Attach the other events through `flow_id`, which is present on every event, including flow events.
  For ICMP, compute the ID the way Suricata does (type with counterpart type, else 0), or match on (ip pair, proto, time) instead, because pycommunityid follows the spec mapping (type, code) and will differ for non-paired types such as dest-unreachable. Verify with a test pcap.
- Suricata flow records include VLAN, so a VLAN-tagged pcap with duplicate tuples across VLANs gives identical Community IDs for different flows. Disambiguate with `vlan`.
- To remove offload-checksum loss in offline captures, run with `-k none` (or `pcap-file.checksum-checks: no` and `stream.checksum-validation: no`) so that packets with bad checksums still reach reassembly, as tshark does. Raise `stream.reassembly.depth` (0 = unlimited) and the libhtp body limits, set `stream.midstream: true`, and use large memcaps to approach tshark completeness.
- `flow_id` is a hash-derived ID per run. Treat it as a join key within one eve.json only, never across runs.

### Gaps
- I found no forum or Redmine thread that confirms or denies whether `pcap_cnt` resets between files queued through unix-socket `pcap-file`. Code reading shows `PcapFileGlobalInit` zeroes it, but I did not trace whether unix-socket mode re-runs it per file. Test it.
- I did not verify which packet's `pcap_cnt` each specific logger uses (for example the TLS event before or after the ServerHello). It depends on the transaction completion progress for each protocol.
- I did not check whether `pcap_cnt` is present on `fileinfo` events for files closed at flow timeout. Presumably it is absent (pseudo-packet).

## 4. Running Suricata from a Python service

### Takeaway
The simplest deterministic integration is one subprocess per pcap: `suricata -r file.pcap -l <outdir> -c <yaml> -k none --runmode single` (optionally with `-S rules` or `--disable-detection`). No capabilities are needed. Unix-socket mode keeps the ruleset loaded and lets you queue pcaps, each with its own output directory, but it processes them one at a time. It mainly saves rule-loading time for large rulesets.

### Cited Findings
- `-r <path>` runs pcap offline mode. A directory input is processed "in order of modified time maintaining flow state between files". `--pcap-file-continuous` keeps running and does not reset flow state between files. `--pcap-file-recursive` and `--pcap-file-delete` also exist. `-l <dir>` sets the log directory. `--runmode <runmode>` overrides the YAML runmode. `-k [all|none]` controls checksums. `-F <file>` applies a BPF filter. `--disable-detection`, `--disable-hashing` and `--set key=value` are available. — [options.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/partials/options.rst)
- `--set` "cannot be used to add new entries to a list". It can only change existing values, and list indexes (for example `outputs.1.eve-log.enabled`) "may change". `--dump-config` shows the indexes. — [options.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/partials/options.rst)
- Unix-socket PCAP mode exists so you can feed "different pcap files to Suricata without having to restart Suricata for each file. This saves time since you don't need to wait for the signature engine to initialize." Start it with `suricata -c x.yaml --unix-socket[=file]`. Commands are `pcap-file <file|dir> <outdir> [tenant] [continuous] [delete-when-done]`, `pcap-file-continuous`, `pcap-file-number`, `pcap-file-list`, `pcap-current`, `pcap-last-processed` and `pcap-interrupt`. You can add multiple files, and "they will be sequentially processed". Paths must be absolute. Ruleset reload commands include `ruleset-reload-rules` and `ruleset-reload-nonblocking`. — [unix-socket.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/unix-socket.rst)
- The unix-socket JSON protocol looks like `{"command":"pcap-file","arguments":{"filename":…, "output-dir":…, "tenant":0, "delete-when-done":true}}`. `output-dir` is mandatory and must exist. Internally there is one running pcap task at a time (`unix_manager_pcap_task_running`), and `PostRunDeinit` runs between files. — [unix-socket.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/unix-socket.rst), [src/runmode-unix-socket.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/runmode-unix-socket.c)
- The `suricatasc` client and other Python tools were "rewritten in Rust" in 8.0, which affects users who import them as Python modules. — [upgrade.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/upgrade.rst)
- Runmodes: "For processing PCAP files … `autofp` is used". The capture thread decodes and hands packets to flow-worker threads. `single` is workers mode with one packet thread, "mostly useful during development". `autofp-scheduler: hash|ippair|ftp-hash`. — [runmodes.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/performance/runmodes.rst), [suricata.yaml.in](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- `stream.reassembly.randomize-chunk-size: yes` is in the default config, along with `toserver-chunk-size`/`toclient-chunk-size: 2560`. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- EVE options for parsing are `threaded: false` (one eve.json), `filetype: regular|unix_stream|unix_dgram|redis` and `pcap-file: true`, which adds `pcap_filename`. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- `pcap-file.buffer-size` (setvbuf, Linux, max 64 MiB, default 128 KiB) and `pcap-file.delete-when-done` are available. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in), [src/source-pcap-file.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/source-pcap-file.c)

### Inferences
- Determinism: use `--runmode single` (one thread, so the eve.json order is stable) and set `randomize-chunk-size: no`, which otherwise varies the raw stream chunking used for detection. App-layer parsing does not depend on chunking, but alert results with stream rules can. Under `autofp`, eve.json line order varies between runs. Sort by `pcap_cnt` and timestamp in Python.
- Capabilities: reading a pcap needs no CAP_NET_RAW or root. Run as the service user and pass `-l` to a writable temp directory, with no `--user`/`--group` or pidfile needed. This is inferred from the pcap-file source mode, which only opens a file. I found no doc stating it explicitly.
- Per-run subprocess suits a service that receives pcaps from Axon. It gives isolation, per-run `--set` overrides (for example per-run decode-as through `app-layer.protocols.X.detection-ports`), simple concurrency (N subprocesses, each with its own `-l`), and crash containment. Unix-socket mode only pays off if a large ruleset (for example ET Open, roughly tens of thousands of rules) is loaded for every run, since engine start-up time is dominated by signature loading. It also serialises runs, so concurrency would need several socket daemons.
- Sizing: the memcaps above (flow 128 MiB, stream 64 MiB, reassembly 256 MiB, defrag 32 MiB) set the ceiling. With `--disable-detection` or no rules, RSS is mostly these memcaps plus app-layer state. With a full ET ruleset, multi-pattern-matcher memory adds several hundred MB. This last figure is not sourced; benchmark it.
- Running app-layer parsing with no rules (`-S /dev/null` or `--disable-detection`) still produces protocol EVE events. File extraction without rules needs `force-filestore: yes`.

### Gaps
- I did not measure start-up time with and without large rulesets, and found no authoritative figure in the sources I read.
- I could not confirm whether unix-socket mode accepts concurrent pcaps. The code and docs point to sequential processing only.

## 6. Gaps where tshark remains necessary

### Takeaway
tshark is still needed for TLS key-log decryption (and therefore TLS 1.3 certificates and HTTP inside TLS), the SSH server host key, SIP User-Agent/Server, exact first-frame-per-item mapping, and a raw .eml when you also want MIME attachment extraction. Suricata covers the rest. With 8.0, its HTTP/2 headers, RDP client data, JA4 and SHA256-named file store are arguably better structured than tshark field extraction.

### Cited Findings
- **TLS decryption: confirmed absent.** Redmine Feature #7796 asks for TLS decryption in pcap mode from SSLKEYLOGFILE files. It is open ("New", no target version) and states that Suricata cannot inspect decrypted content while Wireshark/tshark can. — [Redmine #7796](https://redmine.openinfosecfoundation.org/issues/7796)
- No keylog setting appears in the 8.0 `tls` app-layer config, which offers only `ja3-fingerprints`, `ja4-fingerprints` and `encryption-handling: track-only|bypass|full`. — [suricata.yaml.in 8.0](https://github.com/OISF/suricata/blob/main-8.0.x/suricata.yaml.in)
- **SSH host key: confirmed absent** from the EVE SSH logger. — [rust/src/ssh/logger.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/ssh/logger.rs)
- **SIP User-Agent/Server: confirmed absent** from EVE. The keyword exists for detection only. — [rust/src/sip/log.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/sip/log.rs), [rust/src/sip/detect.rs](https://github.com/OISF/suricata/blob/main-8.0.x/rust/src/sip/detect.rs)
- **Raw .eml:** only through `smtp.raw-extraction` (file "rawmsg"), which is auto-disabled when `decode-mime` is on. You get either attachments and parsed headers, or the raw message, from one run. — [suricata-yaml.rst](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/configuration/suricata-yaml.rst)
- **Per-frame mapping:** `pcap_cnt` is one packet per event (the trigger packet) and is missing on flow and pseudo-packet events. — [EVE format doc](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst), [src/output-json.c](https://github.com/OISF/suricata/blob/main-8.0.x/src/output-json.c)
- RDP certificates: EVE gives only `x509_serials` for RDP over TLS, not the certificate DER. — [EVE format doc RDP](https://github.com/OISF/suricata/blob/main-8.0.x/doc/userguide/output/eve/eve-json-format.rst)

### Inferences
- A hybrid plan works:
  1. Run Suricata for everything EVE supports.
  2. Run tshark selectively: only for TLS flows when a key log is supplied, only on SSH flows (filter `ssh.message_code == 31`) for host keys, and only on SIP flows for UA/Server.
  3. Restrict each tshark pass to the relevant flows with a display or BPF filter built from the Suricata/dpkt flow list. This keeps the cost low.
- Alternative for SSH host keys without tshark: parse KEXDH_REPLY (msg 31, or 33 for ECDH/curve25519 KEX_ECDH_REPLY) in Python from dpkt-reassembled server-to-client bytes. It is unencrypted and appears right after KEXINIT, so a small parser is feasible.
- Alternative for SIP UA without tshark: SIP is plain text and usually UDP, so a few lines of Python over dpkt payloads of flows that Suricata labels `app_proto: sip` can extract `User-Agent:` and `Server:`.
- Alternative for raw .eml together with attachments: run Suricata twice (once with `raw-extraction`, once with MIME), or reassemble the SMTP DATA in Python.
- Things that need verification before claiming parity: RDP over CredSSP/TLS (`hybrid`) hides `connect_request` client data inside TLS, so Suricata (and tshark without keys) can only log client name and keyboard layout for standard-security or non-NLA RDP. This is inferred from the protocol and not tested.
